# Infrastructure — Requirements

What lives where, who runs what, how the pipeline schedules itself.

See also: [Measurement](measurement.md), [Platforms](platforms.md).

## Hosting

The dashboard is served from the `gh-pages` branch of the AWFY
repo. The branch must:

- Be a pure static site (`.nojekyll` at the root disables Jekyll
  processing).
- Contain one root `index.html` (suite chart), one `master.html`
  (master timeline), and one `per-bench/<name>.html` per benchmark
  family.
- Contain one directory per `<ts>_otp..._<sha10>-test-...-`
  run-dir, with `.benchee` files + `meta.json` per run.
- Be regenerated by `mix awfy.compare --out _pages` after every
  publish — *never* hand-edited.

## Runner pools

The bench workflow shall support three runner pools, selected by
the `runner_pool` input on `workflow_dispatch`:

| Pool       | Default for          | Linux                | Windows              | macOS              |
| ---------- | -------------------- | -------------------- | -------------------- | ------------------ |
| `gha`      | push, schedule, all  | `ubuntu-latest`, `ubuntu-24.04-arm` | `windows-2022` | `macos-latest` |
| `aws`      | publication-quality fills | c6i.4xlarge, c7g.4xlarge | c6i.4xlarge       | (none — local M5) |
| (local M5) | macOS only           | n/a                  | n/a                  | M5 hardware        |

Pool-independent invariants:

- **`build-linux` is always GHA-hosted** regardless of pool. Image
  construction doesn't need bare-metal hardware accuracy, and AWS
  measure jobs pull the same image tag from GHCR.
- **Push events force `gha`.** Pushes are smoke tests and must not
  bill the AWS pool.
- **macOS measurements come from the operator's M5** when CI is
  gated off (`measure-macos`'s `if: false`). There is no AWS macOS
  pool in scope.

## AWS Terraform pool

`terraform/main.tf` defines ephemeral self-hosted runners. The
pool shall:

- Use `c6i.4xlarge` for x86_64 (linux + windows), `c7g.4xlarge`
  for arm64 (linux only). Both have 16 vCPU and dedicated cores at
  the VM boundary (no shared tenancy).
- Pin the measure process to **vCPU 0 only** on AWS (the
  workflow's measure step sets `ProcessorAffinity = 1`). vCPU 0's
  hyperthread sibling is vCPU 8 (out of the mask) so the physical
  core has no other scheduled work.
- Spin up per job (ephemeral), shut down after the job completes.
  No long-lived runners.

The pool's purpose is publication-quality measurements (target CV
≤ 5%); the GHA-hosted pool is for smoke + catch-up fills where
noise is tolerable.

## Scheduling

The workflow shall fire on three triggers:

1. `push` to any branch — minimal smoke matrix.
2. `schedule: 0 */6 * * *` — every 6 hours, fill-mode catch-up.
3. `workflow_dispatch` — operator-driven.

The 6-hour cadence is chosen because:
- upstream OTP master lands ~3-4 merges/day → most cron fires
  catch 0-2 new SHAs;
- the 50-merge cap leaves plenty of headroom for an occasional
  busy day or backlog burst;
- macOS local sweeps run on weekend cadence, separately, on M5.

The cron may fire late (GHA hosted-cron jitter is typically 1-3 h).
That's tolerated — the resolver's gap check makes scheduling
idempotent: running early or late, the same gaps get filled.

## Concurrency groups

The workflow's concurrency group shall partition by *purpose*, not
by event source:

    group: ${{ github.event_name == 'push'
               && 'bench-push'
               || format('bench-{0}', inputs.otp_refs || 'fill') }}

- Push smoke runs in `bench-push` — independent of fills.
- Schedule (no inputs → default `fill`) and `workflow_dispatch`
  with the same `otp_refs` share a group → second queues.
- `cancel-in-progress: false` — a late-firing cron must queue, not
  cancel an in-flight manual fill.

This shall guarantee no two writers race the gh-pages publish step.

## Job timeouts

Every job shall set a `timeout-minutes` cap so a hung step doesn't
hold a runner slot indefinitely:

| Job                         | Cap |
| --------------------------- | --- |
| resolve                     | 10  |
| build-linux / *-target      | 30  |
| prep-target-bundle          | 20  |
| measure-linux / *-target    | 60  |
| measure-windows / *-target  | 60  |
| measure-macos / *-target    | 60  |
| measure-xmpp-linux          | 45  |
| publish                     | 90  |

Caps are 1.5–2× the observed happy-path wall-clock. A job past
its cap is by definition hung and should fail so the matrix
unblocks downstream rows.

## Publish step

The publish job shall:

- Use `actions/download-artifact@v8` to gather every measure-*
  job's `results/` output.
- Use `git worktree add _pages origin/gh-pages` to stage commits.
- Wipe gh-pages content (preserving `_pages/.git` + macOS
  run-dirs) only when `otp_refs=all` was dispatched. All other
  modes append.
- Regenerate every HTML page from current gh-pages content via
  `mix awfy.compare --out _pages`.
- Force-touch `_pages/.nojekyll` so GitHub doesn't run Jekyll.
- Commit + push to origin/gh-pages. The commit message records the
  triggering ref, the runner pool, and the count of new run-dirs.

Publish shall run via `if: !cancelled()` so a partial-matrix
failure (one platform's build failed, the others succeeded) still
publishes the rows that succeeded. The publish job itself shall
*not* fail the workflow if the gh-pages push succeeds even when
some upstream measure jobs failed — the green/red conclusion
reflects measure success, not publish success.

## Cost expectations

- **GHA-hosted, public repo:** included in the GitHub Actions
  free tier. No per-fill marginal cost.
- **AWS pool steady-state:** ~$1.50–3 per scheduled fill,
  ~$10/day = **~$300/month** with the 6-hour cadence after the
  backlog clears.
- **AWS pool backlog burn:** ~$100 for an occasional 50-merge
  catch-up dispatch (rare in steady state).

Spot instances would cut AWS cost ~70% but risk mid-bench eviction
→ measurement noise. The c6i / c7g on-demand tier is the
"publication quality" choice; spot is the wrong trade-off for the
trustworthy-numbers invariant.

## Storage

| What                          | Where                                   |
| ----------------------------- | --------------------------------------- |
| Source code                   | `main` branch                           |
| Published dashboard           | `gh-pages` branch                       |
| Published `.benchee` files    | `gh-pages` branch, per run-dir          |
| Per-target OTP build cache    | `~/.ccache` in build-linux job          |
| Per-SHA OTP prefix (local)    | `~/.local/otp/<sha>` on operator hosts  |
| Per-Elixir bundle (legacy)    | `target_bundle_<elixir-version>.tar.gz` |

The gh-pages branch is content-addressed by `<sha10>` — a new
measurement of the same SHA produces a new timestamped run-dir
rather than overwriting. The dashboard's compare task groups
run-dirs per SHA, so multiple measurements of the same commit
are useful (variance estimation) rather than redundant.
